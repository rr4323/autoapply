# `sqlc` — Type-Safe Go from Real SQL

## What it is

A code generator: you write plain SQL (`CREATE TABLE` schema + annotated queries), `sqlc generate` reads it and produces Go structs + query functions with real types — no ORM, no reflection at runtime, no query-building DSL to learn. This is Step 0's choice ("`pgx/v5` + `sqlc`... no ORM guessing, and the SQL stays reviewable") made concrete.

## The three inputs

**Schema** (`sqlc.yaml` points at your migration `.up.sql` files, in order — never `.down.sql`, mixing both would feed `DROP TABLE` statements into the type inference):
```yaml
sql:
  - engine: "postgresql"
    queries: "internal/store/queries"
    schema:
      - "migrations/0001_users_profiles.up.sql"
      - "migrations/0002_episodic_memory.up.sql"
      # ... in order, since later migrations can add FKs to earlier tables
```

**Queries** — plain SQL with a `-- name:` annotation telling sqlc what to generate:
```sql
-- name: CreateApplication :one
INSERT INTO applications (user_id, jd_url, jd_text, company, role_title, source)
VALUES ($1, $2, $3, $4, $5, $6)
RETURNING id, user_id, jd_url, jd_text, company, role_title, source, search_profile_id, jd_fit_score, resume_match_score, score_breakdown_json, scoring_model_version, status, bot_check_detected, submitted_at, created_at, updated_at
```
`:one` = returns a single row (or an error if zero/many); `:many` = returns a slice; `:exec` = no rows returned at all (an `UPDATE`/`DELETE` with nothing to scan back).

**Generated output** (`internal/store/*.sql.go`, `models.go`, `db.go` — all headed `// Code generated by sqlc. DO NOT EDIT.`):
```go
type CreateApplicationParams struct {
	UserID    pgtype.UUID       `json:"user_id"`
	JdUrl     *string           `json:"jd_url"`
	// ...
	Source    ApplicationSource `json:"source"`
}

func (q *Queries) CreateApplication(ctx context.Context, arg CreateApplicationParams) (Application, error) {
	// hand-written-quality scan code, generated
}
```

## What sqlc infers from the schema, automatically

- **Nullable vs. non-null columns** become `*string`/pointer types vs. plain `string` — `jd_url TEXT` (no `NOT NULL`) becomes `*string`; `email TEXT NOT NULL` becomes plain `string`.
- **Postgres `ENUM` types** become real Go types with named constants: `application_status` → `type ApplicationStatus string` + `ApplicationStatusPending`, `ApplicationStatusScored`, etc. — not magic strings scattered through the codebase.
- **`UUID` columns** become `pgtype.UUID` (pgx's own UUID type, since `sql_package: "pgx/v5"` was configured) — matches exactly what `pgxpool` expects to send/receive, no manual conversion layer.

## A real naming collision this project hit

sqlc PascalCases table/type names to generate Go identifiers. `application_outcomes` (table) and `application_outcome` (enum type, singular) both produced the same Go name `ApplicationOutcome` — a hard error, not a warning:
```
error generating code: struct name conflicts with enum name: ApplicationOutcome
```
Fixed by renaming the enum to `outcome_type` in the migration itself — a genuine schema-design fix, not something to work around in generated code (which you can't edit anyway — it says so at the top of every file).

## Standard use case

Any table that needs Go code to read/write it goes through this same three-step loop: write the migration, write annotated queries in `internal/store/queries/`, run `sqlc generate`. `docs/BACKEND_BUILD_STEPS.md` Step 13 used it for `applications`/`profiles`/`application_events`; every later CRUD-needing table in the schema follows the identical pattern.
